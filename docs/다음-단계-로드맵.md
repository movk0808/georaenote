# 거래노트 실서비스 로드맵 (2026-11-12 정리)

지금 있는 것: 안드로이드 앱·웹사이트·웹앱 화면과 흐름(체험판). 데이터는 기기/브라우저에만 저장되고, 결제·본인인증·송금은 모의 처리.
실제로 쓰려면 **① 사업·계약(사람이 할 일)**, **② 서버와 외부 연동(개발)**, **③ 관리자 페이지(개발)**, **④ 출시 준비**가 필요하다.

## ① 사업·계약 — 시간이 가장 오래 걸리니 먼저 시작 (보통 수 주)

| 할 일 | 내용 | 비고 |
|---|---|---|
| PG사 제휴 | 카드 승인·취소·할부·분할결제 + 거래처 계좌로 지급(지급대행) | "소상공인이 외부 공급업체의 실제 매입대금을 카드로 결제하고, 공급업체 계좌로 지급하는 구조를 취급하나요?"를 먼저 묻는다. 여러 PG에 동시에 상담 신청 |
| 법률 검토 | 여신전문금융업법상 신용카드 현금화(카드깡)와 선을 긋는 구조인지, 전자금융업 등록 필요 여부 | 실거래 증빙 심사·이상거래 차단 체계가 핵심. 핀테크 경험 있는 변호사 |
| 본인인증 | PASS를 직접 붙이는 게 아니라 본인인증 대행사(휴대폰 인증 제공사)와 계약하면 통신사·PASS 인증창이 제공됨 | 계좌 실명조회(예금주 확인)도 함께 알아보기 |
| 은행 | **은행마다 연결할 필요 없음.** PG 지급대행이나 펌뱅킹/송금 중계 업체 한 곳이면 모든 은행 계좌로 송금 가능 | 예금주 조회 API도 같은 업체에서 제공하는 경우가 많음 |
| 사업자·세무 | 사업자 업종 확인, 통신판매업 신고, 이용료 매출 증빙 발행, 부가세 처리 | 세무사 |
| 약관·개인정보 | 이용약관, 개인정보처리방침, 위치·마케팅 동의 정식본 | 지금은 초안 |
| 운영 자금 | 바로송금은 거래처에 즉시 지급하지만 PG 카드대금 정산은 며칠 뒤 → 그 사이 지급할 돈(운전자금)이 필요 | 관리자 대시보드에서 '정산 대기 금액 vs 지급 예정 금액'을 꼭 보이게 |

## ② 서버와 외부 연동 (개발)

- 백엔드: 빠르게 시작하려면 Supabase(Postgres + 로그인 + 파일 저장), 직접 운영하려면 Node(NestJS) + Postgres.
- 지금 앱의 저장 부분만 API로 바꾸면 화면은 그대로 쓸 수 있게 만들어 둠
  - 웹: `web/src/lib/store.ts`
  - 앱: `app/.../data/Repository.kt`, `AppViewModel.pay()`, `VerifyScreen`
- 주요 테이블: users, businesses, contracts, contract_documents(증빙), contract_reviews(심사 이력), payments(카드 승인), card_charges(분할 카드), payouts(송금), settlements(PG 정산), fees, mileage_ledger, notices/faqs/articles/events(CMS), inquiries(문의), admin_users, audit_logs
- PG 연동: 결제창 호출 → 승인 → 웹훅 → 송금 지시 → 결과 웹훅. 중복 요청 방지(idempotency), 실패 재시도
- 증빙 파일: 암호화 저장, 심사자만 열람, 열람 기록 남기기
- 알림: 안드로이드 푸시(FCM), 아이폰 웹앱 푸시(홈 화면 앱은 웹 푸시 가능), 카카오 알림톡
- 사업자 진위 확인(국세청 API), 이상거래 탐지(같은 거래처 반복 고액, 본인·가족 계좌 의심, 단기간 급증)
- 보안: 개인정보 암호화, 접근 기록, 관리자 2단계 인증

## ③ 관리자 페이지 (개발)

| 화면 | 보여줄 것 |
|---|---|
| 대시보드 | 일·주·월 결제액(GMV), 이용료 매출, PG 비용, 순이익, 건수, 평균 결제액, 바로/예약 비율, 계약 유형별 비중, 신규·활성 사용자 (그래프) |
| 자금 흐름 | PG 정산 예정액(날짜별) vs 거래처 지급 예정액(예약송금 캘린더) → 필요한 운전자금 |
| 심사 큐 | 새 계약 목록, 증빙 보기, 승인/반려(사유), 처리 시간 SLA, 심사자별 처리량 |
| 결제·송금 | 상태별 목록, 실패 송금 재처리, 취소·환불, 거래 상세(카드·계좌·증빙 연결) |
| 이상거래 | 위험 점수, 차단/보류, 메모 |
| 회원 | 회원·사업자 정보, 계약·송금 이력, 이용 정지 |
| 마일리지·이벤트 | 적립/사용 원장, 퀴즈·첫 송금 이벤트 예산 소진율 |
| 콘텐츠 | 공지, FAQ, 매거진, 할부 정보, 배너 편집 (지금 코드에 박혀 있는 Content.kt / content.json을 여기서 관리) |
| 고객 문의·후기 | 1:1 문의 답변, 후기 승인·노출 관리 |
| 운영 설정 | 이용료율, 한도, 영업일·공휴일, 관리자 권한, 감사 로그 |

## ④ 출시 준비

- 도메인 구입, 웹은 GitHub Pages(화면) + 백엔드 서버 또는 Vercel로 이전
- Play Console 개발자 등록, 금융 서비스 앱 정책·데이터 보안 양식, 개인정보처리방침 URL, 계정 삭제 기능, Play 앱 서명 사용
- 아이폰 정식 앱이 필요하면 Mac + Xcode + Apple 개발자 계정 → 웹앱을 Capacitor로 감싸 빌드
- 서명 키(`keystore/`) 백업
- 소셜 로그인 계정 정리(지금은 개인 계정으로 만든 테스트 설정)
  - 구글: 사업용 구글 계정을 프로젝트 `georaenote`의 소유자로 추가한 뒤 개인 계정을 빼면 돼요(새로 만들 필요 없음). 기본 범위(이메일·프로필)만 써서 100명 제한·인증 심사 대상이 아니에요. 로고를 넣으면 브랜드 인증 심사가 필요해요
  - 카카오: 앱 소유권을 사업용 카카오 계정·팀으로 넘기고, 사업자등록 후 비즈 앱(사업자) 전환 → 이메일 등 동의항목 확대
  - 네이버: 검수 요청 통과 전에는 멤버로 등록한 아이디만 로그인돼요. 사업자 정보로 검수를 받고, 계정 이전이 안 되면 사업용 아이디로 다시 등록(키만 바꾸면 됨)
  - Supabase·GitHub도 사업용 계정 조직으로 옮기기

## 추천 순서

**사람이 바로 시작 (오늘·내일)**: PG사 2~3곳 상담 신청, 법률 검토 요청, 본인인증 대행사 문의, 도메인 구입. 답을 기다리는 동안 개발을 진행한다.

**개발 1일차(내일)**
1. 데이터 모델·DB 스키마 확정 + 백엔드(Supabase 추천) 세팅
2. 관리자 페이지 MVP: 로그인 → 대시보드 그래프 → 심사 큐 → 결제·송금 목록 (테스트 데이터로)
3. 웹앱을 백엔드에 연결(가입·계약·송금이 서버에 저장되게)

**그다음**
4. PG 테스트(샌드박스) 키로 실제 카드 결제창 연동
5. 안드로이드 앱을 같은 API에 연결, 푸시 알림
6. 본인인증·송금·실명조회 실제 연동(계약 후)
7. 이상거래 규칙, 보안 점검 → 비공개 테스트 → 출시
